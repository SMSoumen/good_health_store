01

How it fits together

Every account type — customer, seller, admin, delivery boy, affiliate — lives in a single users table, separated only by role_id. Customers are role_id = 2. Authentication is session-based through the web guard; the storefront does not use API tokens for its own pages.

Auth is implemented mostly as Livewire components under app/Livewire/RegisterAndLogin/ rather than traditional controllers, with a thin AuthController handling SMS OTP and UserController handling logout. The model app/Models/User.php pulls in Spatie roles/permissions and casts password => hashed.

Note: in config/auth.php the api guard is also set to the session driver (Sanctum is commented out), so API-style calls still ride on the web session rather than bearer tokens.
02

The flows

REGISTER

Sign up & social login

app/Livewire/RegisterAndLogin/Register.php
  • Validates username, mobile, unique email, password (confirmed, min 8).
  • Stores a bcrypt password, sets role_id = 2, active = 1, then auto-logs the user in and emails a welcome template.
  • check_mobile_number() pre-checks mobile uniqueness during signup.
  • Google & Facebook via Laravel Socialite — existing email logs in, otherwise a new role_id = 2 account is created.
LOGIN

Mobile + password sign in

app/Livewire/RegisterAndLogin/Login.php · login.blade.php
  • Form binds mobile + password and submits via wire:submit="login".
  • Confirms the mobile exists, blocks accounts where active != 1, then calls Auth::attempt().
  • On success, sends a login-notification email (device / time / timezone) and redirects to /.
  • In demo mode (ALLOW_MODIFICATION == 0) the form pre-fills demo credentials.
OTP

SMS one-time passcode

app/Http/Controllers/AuthController.php
  • send_otp() generates a 6-digit code, saves it to the otps table, and sends it via send_sms().
  • verify_otp() compares the code and flips varified = 1.
RESET

Password recovery

app/Livewire/RegisterAndLogin/ForgetPassword.php
  • check_number() confirms the mobile belongs to a registered user.
  • new_password() re-hashes and writes the new password, keyed on mobile.
LOGOUT

Ending the session

app/Http/Controllers/UserController.php
  • logout() returns JSON with a redirect; Profilelogout() redirects directly — both call Auth::logout().
03

OTP verification method

Admin → System Settings → authentication_method chooses how the mobile number is verified with a one-time code during registration and password recovery — it does not change the main login (mobile + password). The frontend reads a hidden field and branches:

if (authentication_method == "firebase") FirebaseAuth();
else if (authentication_method == "sms") CustomSmsAuth();
Option 1 · firebase

Firebase Authentication

OTP sent & verified by Google
  • Loads Firebase web config from settings/get-firebase-credentials (the firebase_settings saved in admin) and renders a reCAPTCHA.
  • Send → firebase.auth().signInWithPhoneNumber() — Google's infrastructure delivers the SMS.
  • Verify → confirmationResult.confirm(code) — checked client-side by Firebase.
  • Your AuthController and the otps table are not used.
Setup: Firebase project with Phone auth, web API keys in admin, domain added to authorized domains. Google handles delivery, anti-abuse & rate limits; SMS is billed by Google past the free tier.
Option 2 · sms

Custom SMS Gateway OTP

OTP generated & verified on your server
  • Send → POST auth/send_otp → generates a 6-digit code, stores it in the otps table, sends it through your gateway via send_sms().
  • Verify → POST auth/verify_otp → compares the code and flips varified = 1.
  • Uses whatever provider you set in SMS Gateway settings (Twilio, MSG91, …).
Setup: SMS gateway credentials in admin. You control sender ID, cost & regional reach — but you own delivery reliability, expiry and abuse protection.
Caveat

The method is only a delivery channel — not enforcement

In both modes the OTP is checked in the browser. In sms mode verify_otp only sets a flag that the reset flow never re-checks server-side; in firebase mode verification never touches your backend at all. A request sent straight to /register/submit or the password-reset endpoint bypasses either method. See finding 01 below.

05

Security findings

Ranked most severe first. The first two are account-takeover risks and should be treated as blockers.

Critical

Password reset has no server-side verification

new_password() updates any account's password given only a mobile number + new password. It never checks the OTP varified flag or any token — the OTP step is enforced only in the frontend. Anyone POSTing to /password-recovery/set-new-password can take over any account by phone number.

Fix Require a verified, unexpired otps record for that mobile before writing the password, then consume it.
Critical

OTPs never expire and are reusable

verify_otp() has no expiry timestamp, no rate limiting, and never clears the code after use. A code stays valid indefinitely and can be replayed — which compounds the reset flaw above.

Fix Add a created_at expiry window, throttle send/verify attempts, and delete the row once consumed.
Warning

Customer login is not role-scoped

login() authenticates any row in users by mobile + password without checking role_id. An admin or seller can authenticate through the customer form into the same web session, and vice versa.

Fix Scope Auth::attempt() to role_id = 2 on the storefront login, or gate privileged areas by role explicitly.
Info

Registration uses the framework base User model

Register.php imports Illuminate\Foundation\Auth\User instead of App\Models\User, so User::create() bypasses the app model's $fillable and $casts. It works today (same table) but is fragile and inconsistent with the rest of the codebase.

Fix Import and use App\Models\User for all writes.
